# HLA64 для Linux x86-64

Тот же язык, третья нативная платформа: транслятор выдаёт ассемблер x86-64 для ABI System V (синтаксис
Intel в диалекте LLVM, его понимают `clang`, `gcc` и встроенный ассемблер), дальше — свои объектные файлы
ELF, линковщик ELF с динамической линковкой к glibc и эмулятор x64 с загрузчиком ELF. Всё работает и в Node,
и на странице `dist/hla64.html` (**Platform: Linux**).

```
prog.hla ─► src/lang/x64 ─► .s (Intel, System V) ─► src/asm/x64 ─► ELF .o ─► src/asm/elf/link.ts ─► prog (ELF, libc.so.6)
                                                                     │
                                                     libname.a (ar), libname.so
```

## Командная строка

На Linux платформа по умолчанию `x64-linux`; на других системах её выбирают через `--target x64-linux`:

```sh
node src/cli.ts run   examples/hello.hla --target x64-linux   # вне Linux x86-64 — во встроенном эмуляторе x64
node src/cli.ts build examples/hello.hla --target x64-linux   # hello (исполняемый ELF, chmod +x уже сделан)
node src/cli.ts compile prog.hla --target x64-linux           # ассемблер x86-64
node src/cli.ts obj   app.hla --target x64-linux              # app.o для gcc / clang / ld
node src/cli.ts lib   mathlib.hla --target x64-linux          # mathlib.h, mathlib.o, libmathlib.a, libmathlib.so
node src/cli.ts emu   prog --target x64-linux                 # ELF-файл, собранный где угодно (и gcc тоже), в эмуляторе
node src/cli.ts build prog.hla --target x64-linux --clang     # сборка через cc на Linux, через zig cc на других системах
node src/cli.ts run   prog.hla -- one "two words"             # аргументы после -- попадают в main(argc, argv) (и в emu)
```

`--clang` собирает тот же ассемблер системным компилятором C с той же точкой входа
(`cc -nostartfiles -Wl,-e,hla_start prog.s -lm`). Вне Linux используется `zig cc -target x86_64-linux-gnu` —
это clang и lld с заглушками библиотек glibc: исполняемый файл для Linux можно собрать на macOS или Windows
без Linux. `emu` запускает любой исполняемый файл Linux x86-64, в том числе собранный gcc или clang;
нужные ему разделяемые библиотеки (кроме glibc) берутся из той же папки.

## Регистры и соглашение о вызовах (System V)

| | |
|---|---|
| целые аргументы | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, дальше стек |
| аргументы с плавающей точкой | `xmm0`–`xmm7`, **счёт отдельно от целых**: `f(a, x: f64, b)` — `a` в `rdi`, `x` в `xmm0`, `b` в `rsi` |
| вызовы с переменным числом аргументов | `al` = число xmm-регистров с аргументами (`printf("%f", x)` ставит `mov eax, 1`) |
| результат | `rax` / `xmm0` |
| портятся вызовом | `rax rcx rdx rsi rdi r8–r11`, все xmm-регистры |
| сохраняются | `rbx rbp r12–r15` — пролог сохраняет те, что встречаются в функции |
| `let x = …` без регистра | один из `rbx r12–r15 rbp` (их 6; на Windows 8, на ARM 10), дальше — ячейка во фрейме |
| рабочие регистры транслятора | `r10`, `r11` (+ свободные сохраняемые), `xmm15` вниз до `xmm8`, которые функция не называет (`xmm4`–`xmm7` здесь несут аргументы) |

Чтобы один и тот же код для x64 работал на Windows и на Linux, **`rsi`, `rdi` и `xmm6`–`xmm15`, названные в
функции, сохраняют значения при её вызовах и на Linux**: перед каждым вызовом (C, HLA64 или `syscall`)
транслятор кладёт их во фрейм и возвращает после — в ассемблере это видно как
`// keep rsi, xmm6 across the call`. Переменные в `rbx`, `r12`–`r15`, `rbp` (и любой `let` без регистра)
ничего не стоят; параметр без регистра остаётся в своём регистре аргумента и, как на Windows (`rcx`, `rdx`),
вызов не переживает — чтобы сохранить его, пишите `n: auto`.

```hla
extern printf(fmt, ...)

fn hypot(a: xmm0, b: xmm1) {
    return sqrt(a * a + b * b)
}

fn main() {
    let r: xmm6 = 2.0                    // сохраняется при вызовах ниже
    xmm0 = hypot(3.0, r * 2.0)
    printf("%.1f %.1f\n", xmm0, r)       // xmm0, xmm1 и al = 2
}
```

Фрейм адресуется от `rsp` (без `rbp`), место для исходящих аргументов выделяется один раз в прологе, при
каждом вызове `rsp` выровнен на 16 байт, как требует glibc. Нет ни `.seh_*`, ни теневой области.

## Чем отличается от Windows x64

- `printf("%ld")` печатает 64 бита, как на macOS (`long` на Linux 64-битный).
- **`syscall(номер, ...)`** работает: номер идёт в `rax`, аргументы — в `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9`,
  затем выполняется инструкция `syscall` (ядро меняет `rax`, `rcx`, `r11`). Номера линуксовые, не как на macOS:
  `1` write, `0` read, `39` getpid, `60` exit, `231` exit_group. Пример —
  [tests/linux/cases/syscall.hla](../../tests/linux/cases/syscall.hla).
- Инструкции, написанные руками, следуют System V: первый аргумент `naked`-функции лежит в `rdi`
  (`lea rax, [rdi + rdi]`), а голый `call puts` ждёт строку в `rdi` и выровненный `rsp`. Пример —
  [tests/linux/cases/mixed.hla](../../tests/linux/cases/mixed.hla).
- Функции `extern` вызываются напрямую (`call printf`); линковщик превращает вызов в заглушку
  `jmp qword ptr [rip + GOT]`. Адрес `extern` (функция C как значение, `stdout`, `environ`) берётся из GOT:
  `mov rax, qword ptr [rip + stdout@GOTPCREL]`. До переменных glibc можно добраться только так — `call stdout`
  или `[rip + stdout]` линковщик считает ошибкой. Пример —
  [tests/linux/cases/extern-data.hla](../../tests/linux/cases/extern-data.hla).
- Программа начинается с `hla_start`: ядро оставляет на стеке `argc`, `argv`, `envp`, glibc к этому моменту уже
  инициализирован динамическим загрузчиком, `hla_start` регистрирует через `__cxa_atexit` функцию загрузчика
  `_dl_fini` (она приходит в `rdx`), как это делает стартовый код самой glibc, — поэтому при выходе работают
  деструкторы разделяемых библиотек, — затем вызывает `main(argc, argv, envp)` и завершает процесс через `exit()`
  (он сбрасывает буферы `printf`).
- Линковщик берёт каждый `extern` из библиотеки, которая его экспортирует: `libc.so.6` или `libm.so.6` (`sin`,
  `pow` — в libm; списки экспорта glibc 2.35 встроены — [src/asm/elf/glibc.ts](../../src/asm/elf/glibc.ts),
  обновляются `node tools/gen-glibc.ts`). Имя, которого нет ни там, ни там (опечатка), — ошибка сборки с
  номером строки. Каждая ссылка просит версию символа по умолчанию, как её записывает `ld` (`memcpy@GLIBC_2.14`,
  `realpath@GLIBC_2.3`; `.gnu.version_r`): без версий glibc привязала бы самую старую совместимую версию каждой
  функции. Ничего новее glibc 2.35 не запрашивается, так что программа работает на Ubuntu 22.04 и новее.
- Комментарии после кода в ассемблере пишутся `# заметка`: GNU `as` (за gcc) читает там `//` как деление;
  комментарий `// заметка` на всю строку остаётся.

## Исполняемый файл

Не-PIE `ET_EXEC` по адресу `0x400000`, динамически связанный с glibc через `/lib64/ld-linux-x86-64.so.2`:

| сегмент | содержимое |
|---|---|
| `R` | заголовок ELF, заголовки программы, `.interp`, `.hash`, `.dynsym`, `.dynstr`, `.gnu.version`, `.gnu.version_r`, `.rela.dyn` |
| `R X` | `.text` и заглушки импортируемых функций |
| `R` | `.rodata` (строки, константы, литералы `double`) |
| `RW` | `.dynamic`, `.got`, `.data`, `.bss` |

Каждый сегмент в памяти начинается с новой страницы, а в файле они идут подряд (hello world — около 3 КБ).
`DT_FLAGS = BIND_NOW`: динамический загрузчик заполняет весь GOT (`R_X86_64_GLOB_DAT`) до старта программы,
ленивой привязки нет. `PT_GNU_STACK` делает стек неисполняемым. `.symtab` и заголовки секций сохраняются, так
что `nm`, `objdump -d` и `gdb` видят имена функций.

## Библиотеки для C

`lib --target x64-linux` создаёт:

| файл | зачем |
|---|---|
| `name.h` | заголовок (обычные объявления C, `_Static_assert` для раскладки структур) |
| `libname.a` | статическая библиотека (архив GNU `ar` с `name.o`) |
| `libname.so` | разделяемая библиотека (`DT_SONAME libname.so`, позиционно-независимая) |
| `name.o` | объектный файл |

```sh
cc main.c libmathlib.a -o demo                                   # статически
cc main.c -L. -lmathlib -Wl,-rpath,'$ORIGIN' -o demo             # с libmathlib.so рядом с программой
```

Программа на C, собранная без PIE, которая читает переменную библиотеки (`call_count` в уроке 14), получает
собственную копию этой переменной (copy relocation). Поэтому библиотека для Linux, сделанная HLA64, обращается к
своим экспортируемым переменным через свой GOT, как код с `-fPIC`, и обе стороны работают с одной копией.
Объектный файл тоже позиционно-независимый: `cc -shared name.o -o libname.so` работает. Библиотека может
вызывать функцию, которую определяет программа на C (`extern guarded`): динамический загрузчик найдёт её в
программе при запуске.

В обратную сторону, программа на HLA64 вызывает C: `node src/cli.ts obj app.hla --target x64-linux`, затем
`cc app.o helpers.c -o app` (точка входа рантайма C вызывает `main`) или
`cc -nostartfiles -Wl,-e,hla_start app.o helpers.c -o app`. Полный пример:
[tests/linux/lib](../../tests/linux/lib) вместе с [tests/x64/lib](../../tests/x64/lib).

## Эмулятор

Эмулятор x64 загружает исполняемые файлы ELF и нужные им разделяемые библиотеки, применяет динамические
релокации (`RELATIVE`, `GLOB_DAT`, `JUMP_SLOT`, `64`, `COPY`, TLS), строит стек процесса так же, как ядро (`argc`,
`argv`, `envp`, `auxv`), и даёт функции glibc на JavaScript: `printf` и родственники, потоки `FILE` и файлы,
`malloc`, `qsort` с обратным вызовом, `math.h`, `rand()` с той же последовательностью, что у glibc,
`__libc_start_main` для программ, собранных gcc или clang, `fs:` и блок управления потоком (защита стека читает
свою «канарейку» по адресу `fs:0x28`). Как и настоящий код библиотеки, эмулятор требует соблюдать ABI там, где
настоящий Linux упал бы или напечатал мусор, и говорит об этом прямо:

- при каждом вызове библиотеки C `rsp` выровнен на 16 байт;
- вызову с переменным числом аргументов, который передаёт `double`, нужен `al` > 0;
- вызовы библиотеки оставляют мусор в `rdi rsi rdx rcx r8–r11` и во всех xmm-регистрах;
- функция, вызванная из C (обратный вызов `qsort`), сохраняет `rbx rbp r12–r15` и `rsp`.

## Страница

**Platform: Linux** переключает примеры (вызовы System V, `syscall`, обзор языка с системным вызовом), вкладки
(**ELF**: заголовок, сегменты, секции, импорт по библиотекам, экспорт `.so`) и загрузки: **Download executable**
даёт ELF-файл (сделайте ему `chmod +x` или возьмите `.zip`, где бит сохранён), **Copy Terminal command**
воссоздаёт файл из base64 в терминале Linux. Для библиотек — zip с `.h`, `.a` или `.so`, `main.c` и `build.sh`.
