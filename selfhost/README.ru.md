Здесь лежат транслятор и ассемблер HLA64, написанные на самом HLA64. Они собирают сами себя
и готовые программы для двух платформ, без TypeScript-версии из `src/`:

| программа | что делает | исходник |
|---|---|---|
| `hlc-arm` | HLA64 → ассемблер AArch64 (macOS) | [hlc-arm.hla](hlc-arm.hla) |
| `hlc-x64` | HLA64 → ассемблер x86-64 (Windows) | [hlc-x64.hla](hlc-x64.hla) |
| `hlas-arm` | ассемблер AArch64 → подписанный исполняемый Mach-O | [hlas-arm.hla](hlas-arm.hla) |
| `hlas-x64` | ассемблер x86-64 → исполняемый PE (`.exe`) | [hlas-x64.hla](hlas-x64.hla) |

```sh
hlc-arm  prog.hla prog.s      # транслятор
hlas-arm prog.s   prog        # ассемблер и компоновщик: готовая программа для macOS
./prog
```

Платформа, на которой работает инструмент, и платформа, для которой он пишет код, не связаны.
Любой из четырёх собирается и для macOS, и для Windows: например, `hlc-x64`, собранный для
macOS, пишет ассемблер для Windows.

## В браузере

В воркбенче (`./build.sh open`) на обеих платформах есть два примера. Каждый инструмент там —
проект со своими исходниками:

| пример | главный файл | аргументы | результат |
|---|---|---|---|
| **Translator in HLA64 (hla → s)** | `hlc-arm.hla` | `hello.hla hello.s` | `hello.s` появляется в проекте |
| | `hlc-x64.hla` | `hello.hla hello-x64.s` | `hello-x64.s` |
| **Assembler in HLA64 (s → executable)** | `hlas-arm.hla` | `hello.s hello` | исполняемый файл macOS |
| | `hlas-x64.hla` | `hello-x64.s hello.exe` | исполняемый файл Windows |

- При открытии пример сразу запускает свой инструмент в эмуляторе на файлах проекта.
- Второй инструмент пары становится главным по ▶ в списке Files. Командная строка задаётся в
  строке Arguments над консолью.
- Текстовые файлы, которые пишет инструмент, становятся файлами проекта. Двоичные файлы
  показываются в консоли с кнопками Run (запустить в эмуляторе) и Download.
- Download executable (на Windows Download .exe) сохраняет сам инструмент, собранный для
  выбранной платформы.
- `hello.s` и `hello-x64.s` в примере ассемблера сделаны `hlc` из `hello.hla`. `test.sh`
  проверяет, что они не устарели.

`npm run check:selfhost-web` проходит обе цепочки на обеих платформах в headless Chrome.

## Как собрать и проверить

```sh
./test.sh         # всё: macOS и Windows (программы для Windows запускаются во встроенном эмуляторе x64)
./test.sh arm     # только AArch64
```

Нужен Node 24+ — только для первой сборки (раскрутки) и как эталон для сравнения. Всё
складывается в `build/`. Скрипт проверяет:

1. **Раскрутка.** `hlc1` и `hlas1` собирает TypeScript-тулчейн (`node ../src/cli.ts build`).
2. **Свой тулчейн.** `hlc1` транслирует `hlc-arm.hla` и `hlas-arm.hla`, `hlas1` собирает из
   этого `hlc2` и `hlas2`. Исполняемые файлы **побайтно совпадают** с результатом
   TypeScript-компоновщика.
3. **Неподвижная точка.** `hlc2` и `hlas2` пересобирают себя и дают те же байты. С этого
   момента TypeScript не нужен.
4. **Тесты** `tests/**/*.hla`: `hlc2` + `hlas2`, запуск, сравнение с `.expected`. Для каждой
   программы исполняемый файл ещё раз сверяется с TypeScript-компоновщиком. Файлы `.error`
   задают ожидаемое сообщение об ошибке.
5–8. **Windows.** Те же инструменты для x86-64: `hlc.exe` и `hlas.exe` побайтно равны
   результату TypeScript-компоновщика PE. Тесты запускаются в эмуляторе x64. В эмуляторе
   `hlc.exe` и `hlas.exe` пересобирают себя и дают те же байты.
9. **Пример воркбенча.** TypeScript-транслятор собирает все четыре инструмента для Windows, как это
   делает пример в браузере. В эмуляторе они собирают `hello.hla`, и результат побайтно
   совпадает с результатом здешних инструментов.

На настоящей Windows `.exe` из `build/w/` запускаются как есть: `hlc.exe prog.hla prog.s`,
`hlas.exe prog.s prog.exe`.

## Устройство

```
hello.hla   программа для примеров; hello.s, hello-x64.s — то, что из неё делает hlc
lib/        переносимый слой и общие библиотеки
  sys.hla       ОС: память, файлы, вывод, exit — только функции C runtime, которые есть
                и в libSystem (macOS), и в msvcrt.dll (Windows)
  text.hla      строки, растущий буфер Buf, форматирование (%d %s %c) без printf
  intern.hla    таблица имён: каждое имя хранится один раз и известно по номеру
  sha256.hla    SHA-256 (UUID и подпись кода Mach-O)
front/      транслятор: общая часть для обеих платформ
  lexer.hla     текст → токены; здесь же include (каждый файл один раз)
  names.hla     ключевые слова, типы, смысл имён верхнего уровня
  ast.hla       узлы синтаксического дерева
  parser.hla    токены → дерево; объявления верхнего уровня сразу попадают в таблицу имён
  consts.hla    константы, sizeof/len, раскладка данных
  codegen.hla   дерево → вызовы бэкенда be_* (стековая машина с аккумулятором)
  driver.hla    main: hlc input.hla output.s
arm/backend.hla   be_* для AArch64: x0 — аккумулятор, x1 — второй операнд
x64/backend.hla   be_* для x86-64: rax и rcx, соглашение Win64, SEH-директивы, hla_start
asm/core.hla      общее для ассемблеров: секции, символы, фиксапы, разбор строки, директивы данных
arm/encode.hla    инструкции AArch64 → машинные слова
arm/macho.hla     компоновка Mach-O: стабы и GOT для libSystem, bind/rebase dyld, подпись
x64/xenc.hla      инструкции x86-64 → байты (REX, ModRM, SIB — как у LLVM)
x64/xasm.hla      секции COFF, подгонка коротких/длинных переходов, .xdata/.pdata из .seh_*
x64/pe.hla        компоновка PE: импорт из DLL, стабы jmp [IAT], базовые релокации
x64/winapi.hla    имена, которые экспортируют msvcrt/kernel32/user32 (генерирует gen-winapi.ts)
```

Транслятор — классический: токены → дерево → код. Генератор кода (`front/codegen.hla`) ничего не
знает о процессоре: он вызывает `be_num`, `be_push`, `be_binop`, `be_call`… Каждая переменная
(`let`, параметр) живёт в 8-байтовой ячейке кадра стека, поэтому значения переживают вызовы
без распределения регистров. Код получается простым и предсказуемым, но медленнее, чем у
TypeScript-транслятора. Второй бэкенд — это один файл с теми же функциями `be_*`.

## Какой HLA64 понимает hlc

Подмножество языка без регистров — ровно то, на чём написан сам тулчейн:

- верхний уровень: `fn` (в том числе `export fn`), `extern f, printf(fmt, ...)`, `const`, `enum`,
  `struct` (поля, вложенные структуры, массивы), `data`/`rodata` (скаляры, массивы, строки,
  таблицы указателей на строки и функции), `include`;
- операторы: `let`/`var`, `local name: type[N]`, `local name: type = value`, `local name = value`,
  присваивания (`=`, `+=` … `>>>=`, `++`, `--`),
  `if`/`elif`/`else`, `while`, `do … while`, `loop`, `for i in a..b step k`, `break`,
  `continue`, `return`, `switch`/`case`/`default`;
- выражения: все операторы с приоритетами Go, `?:`, вызовы (в том числе через переменную
  с адресом функции), `[addr]`, `u8[addr]` … `i64[addr]`, `array[i]`, `&x`, `sizeof`, `len`,
  `Struct.field`, `Enum.member`.

Нет: имён регистров и `asm`, плавающей точки, `unsigned`, меток циклов, встроенных функций
(`min`, `abs` …), `std/…`. Встретив такое, транслятор сообщает об ошибке с файлом и строкой.

Ассемблеры понимают всё, что пишут трансляторы этого каталога и TypeScript-версия для таких
программ. Кроме того, `hlas-arm` знает `ldp/stp`, `csel`, `tst`, сдвиги и расширения,
`hlas-x64` — `imul`, `movabs`, `cmovcc`, `push imm` и т. п. Логических immediate-масок ARM
(`and x0, x1, #0xff`) и SSE пока нет.

## Как писать код, который собирают оба транслятора

Исходники здесь собирает и TypeScript-транслятор (для раскрутки), поэтому они соблюдают его
правила:

- параметр, который нужен после вызова, объявляется как `name: auto` (иначе он живёт в `x0…x7`
  и портится вызовом);
- имена переменных не совпадают с регистрами ни одной платформы: `x1`, `s0`, `ch`, `si`, `cl`,
  `rsp`…
- поле структуры нельзя назвать `size` (это `Struct.size`), а член enum — `count`.

Вызовы можно писать в любом месте выражения (`[n + Node.a] = parse_expr()`, `f(a) + g(b)`),
выражения вычисляются слева направо, а граница `for i in a..b` — один раз. Оба транслятора
делают это одинаково.

Пока писался этот каталог, в TypeScript-трансляторе нашлись и исправлены две ошибки: условие
`elif` или цикла сразу после тела, где менялась вытесненная в кадр переменная, и запись в узкую
память значения, которому нужны все 64 бита (`u8[p] = n >>> 40`). Кроме того, x64-транслятор
отказывался от выражений вроде `[table + [p + 8] * 8]` в функциях, где все callee-saved регистры
заняты переменными. Теперь он сам переносит переменные в кадр стека, пока выражения не поместятся.
А в язык добавлен `switch`.
